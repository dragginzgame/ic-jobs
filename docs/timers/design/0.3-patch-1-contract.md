## Current implementation inventory

Version 0.2.0 contains:

- a public pure `TimerControl` with mutually exclusive `Unregistered`,
  `Scheduled`, and `Running` states;
- a public direct `platform` module with a copyable provider handle and public
  one-shot arm/clear functions;
- checked `TimerDirective` deadline conversion;
- freely constructible snapshot structs with public fields;
- representational `Watchdog`, pre-armed-successor, interruption, elapsed-time,
  and epoch values; and
- no registry, live callback owner, lifecycle reconstruction, measurement, or
  PocketIC runtime evidence.

Those pure types remain the truthful 0.2 boundary. They are not a partial live
watchdog implementation.

The 0.3 hard cut makes the live registry the only public mutation authority.
`control` and `platform` become crate-private implementation modules. Provider
handles become non-`Copy`, non-`Clone`, and never cross the public API.

## Downstream inventory

The maintained Canic timer authority has five closed built-in identities:

- authentication renewal;
- cycle top-up;
- intent cleanup;
- log retention; and
- placement receipt acknowledgement.

Canic additionally owns one control-plane canister-pool maintenance interval,
short-lived lifecycle one-shots, and a dynamic application one-shot/interval
facade. Its built-in work is asynchronous and uses `Stop`, immediate
continuation, retry-after, and absolute-deadline decisions. Its application
interval uses fixed after-completion recurrence.

IcyDB owns one generated recovery watchdog per generated database domain. The
accepted use is synchronous, fixed at one second, and needs only `Continue` or
`Stop`. The application readiness fixture separately owns a short-lived retry
timer; it is not part of database recovery authority.

No downstream inventory justifies caller-selected watchdog cadence changes,
persisted timer state, a second executor, or a query-side driving path.

## Registry capacity

The fixed capacity is:

```text
MAX_TIMER_REGISTRATIONS = 64
```

The bound counts declared registry entries, not queued provider heap records.
It leaves 56 or more entries after the currently known Canic built-ins,
control-plane interval, IcyDB watchdog, and a lifecycle one-shot are present.
Dynamic application registration beyond the bound returns a typed capacity
error without arming a provider callback or changing existing entries.

An ordinary entry owns at most one live provider handle. A watchdog owns at
most two: one scheduler successor and one queued immediate work callback. The
worst-case all-watchdog registry therefore owns at most 128 live handles.
That is an `ic-timers` ownership bound, not proof of spare provider dispatch
capacity: the pinned provider's 250 outstanding-call semaphore is
canister-wide and may also be consumed by direct provider users. Provider
tombstones are not registry handles and remain the provider's implementation
detail.

Canic's current application facade is infallible, while this registry has a
real capacity error and each identity component has a 64-byte UTF-8 bound. Its
adapter must hard-cut `set` and `set_interval` (and their macros) to return a
typed registration result. It must propagate capacity and identity validation
without panic, eviction, or silent truncation. Closed built-in identities are
prevalidated and registered before application hooks; a built-in failure is a
lifecycle failure, not a best-effort omission. Dynamic application identities
include the monotonic application ID so repeated labels remain unique. Canic's
existing 96-byte status-name allowance must be reduced or explicitly encoded
into valid 64-byte components, with focused projection tests preserving the
operator label. This is a Canic adapter decision and does not alter the IcyDB
watchdog contract.

The inventory is stored in a `BTreeMap<TimerIdentity, Entry>` so lookup is
bounded by capacity and full snapshots are deterministically ordered without a
second sort or index.

## Registration and ownership API

Registration is policy-specific so watchdog work cannot accidentally become
async and ordinary Canic work retains its required future-based surface. The
planned API families are equivalent to:

```rust,ignore
register_once(identity, lifetime, async_work) -> Result<OnceRegistration, RegisterError>
register_after_completion(identity, cadence, lifetime, async_work)
    -> Result<AfterCompletionRegistration, RegisterError>
register_watchdog(identity, cadence, sync_work)
    -> Result<WatchdogRegistration, RegisterError>
```

Ordinary work is an erased `FnMut(TimerContext) -> Future<Output =
TimerRunResult>`. Watchdog work is an erased synchronous
`FnMut(TimerContext) -> WatchdogRunResult`. Every callback is `'static` and
stored only in the canonical entry.

Registration handles are opaque, non-`Copy` logical claims containing the
identity and a runtime-local claim generation. They do not contain provider
handles. Methods validate both values so a handle made stale by unregistration
cannot mutate a later claim for the same identity.

The first registration claims the identity. A repeated registration returns a
typed `IdentityAlreadyRegistered` result and performs no mutation, callback
replacement, provider arm, or counter change. This is the safe idempotent
property available when erased closures cannot be compared: repeating the
operation is harmless and deterministic, but cannot silently grant ownership
of the first caller's callback.

Repeated `ensure_scheduled`, `cancel`, and lifecycle reconciliation on the
valid registration handle are successful idempotent operations. Reconstruction
after upgrade registers anew because the heap registry and old handle no
longer exist.

`TimerContext` is passed to work after the registry borrow is released. It
supports nested ensure and cancellation without requiring a consumer to
capture its registration handle. Mutation validates the exact identity, claim
generation, callback generation, work role, and currently running state. A
context retained after work returns expires; its identity remains inspectable,
but it cannot mutate a scheduled successor or a later registration.

After a public registration or lifecycle operation emits a pure registry
effect, the runtime must either establish exact provider-handle ownership and
confirm the arm counters or fail the declaration closed. An unexpected
installation or confirmation failure clears newly armed and replaced handles;
a retained declaration becomes inactive with `ProviderBindingFailed` and may
be explicitly ensured again. It must not remain observably scheduled without
an owned provider handle.

## Declaration lifetime

Declaration lifetime is distinct from scheduling policy:

- `Retained` keeps an inactive declaration and its callback after `Stop` or
  cancellation. IcyDB and Canic built-ins use this so later durable demand can
  call `ensure_scheduled` without recreating callback authority.
- `RemoveWhenStopped` removes an entry after terminal completion or
  cancellation. Dynamic application one-shots and intervals use this so a
  bounded registry does not accumulate completed application timers.

Explicit unregistration consumes the logical registration handle. If work is
active, removal is deferred through the same request arbitration as nested
cancellation. A trap rolls work-message unregistration back together with the
rest of that work message.

## Cadence and scheduling values

Recurring cadence uses a validated `TimerCadence` value:

- encoded nanoseconds must be nonzero;
- `Duration::as_nanos()` must fit in `u64`;
- successor calculation uses checked `now + cadence`; and
- a checked overflow is a typed terminal control failure that does not invoke
  work.

`TimerPolicy` stores `TimerCadence` rather than a publicly constructible raw
`u64`. A `Once` registration has no default cadence and is initially scheduled
with an explicit checked delay or absolute deadline. `AfterCompletion` and
`Watchdog` use their configured cadence for their initial `ensure_scheduled`
request.

An absolute deadline at or before current IC time is armed with zero delay. A
missed watchdog successor is never replayed from its historical deadline; the
scheduler uses its actual dispatch time for the next checked successor.

## Policy and directive matrix

`Once` means no automatic recurrence. Its repeatable async callback may still
make an explicit next-run decision:

| Directive | Once | AfterCompletion | Watchdog |
| --- | --- | --- | --- |
| `Stop` | yes | yes | separate `Stop` decision |
| `ContinueImmediately` | yes | yes | no |
| `RetryAfter(delay)` | yes | yes | no |
| `ScheduleAt(deadline)` | yes | yes | no |
| `RecurAfterCompletion` | no | yes; uses configured cadence | no |
| `Continue` | no | no | separate `Continue` decision retaining the pre-armed successor |

Version 0.3 hard-cuts `RecurAfter(Duration)` to the parameterless
`RecurAfterCompletion`; configured cadence has one owner and cannot disagree
with a callback-provided interval.

`TimerRunResult` combines a completion class, bounded work count, and legal
ordinary directive. `WatchdogRunResult` combines the same completion and work
count with `Continue | Stop`. Constructors keep fields private and force an
invariant-failure completion to `Stop` for every policy.

Success and valid no-work reset the consecutive expected-failure streak.
Retryable failure increments it with saturation. Invariant failure resets the
streak and stops. A watchdog retryable failure may return `Continue`; its
already committed fixed-cadence successor remains authoritative.

## Nested request arbitration

Consumer work runs with no registry borrow. Nested commands use a monotonic
request sequence:

- repeated ensure requests coalesce without another equivalent arm;
- multiple pending schedules retain the earliest requested deadline;
- authoritative reconciliation replaces an earlier or later deadline;
- cancellation after scheduling wins;
- ensure after cancellation re-enables the retained declaration; and
- a nested command received during work overrides the callback's returned
directive when completion commits.

The registry owns the one pending ordinary command and its scheduling metadata.
`TimerControl` owns generation/registration transitions but no second pending
command, so completion cannot arbitrate the same requests twice.

For a watchdog, `ensure_scheduled` while its successor is already authoritative
is a coalesced no-op. Cancellation clears the owned successor and any still
queued work handle and rotates both scheduler and attempt generations. An
ensure after that cancellation arms one new scheduler relative to current
time. A trap rolls all nested work-message commands back and leaves the
successor committed by the earlier scheduler message intact.

## Policy-specific state

The flat 0.2 `registration + in_flight + optional pre_armed_successor` shape is
replaced by closed policy-specific snapshot state with private fields and
read-only accessors:

```rust,ignore
enum TimerRuntimeStateSnapshot {
    Inactive { reason: InactiveReason },
    Ordinary(OrdinaryRuntimeStateSnapshot),
    Watchdog(WatchdogRuntimeStateSnapshot),
}

enum OrdinaryRuntimeStateSnapshot {
    Scheduled { generation, deadline_ns },
    Running { generation },
}

enum WatchdogRuntimeStateSnapshot {
    Scheduled { scheduler_generation, deadline_ns },
    AwaitingWork {
        successor_generation,
        successor_deadline_ns,
        attempt: WatchdogAttemptSnapshot,
    },
}

enum WatchdogAttemptStatus {
    Dispatched,
    Running,
}
```

`Running` watchdog attempt state is observable to nested consumer inspection
during a normally executing work message. If work traps, that state rolls back
to the previously committed `Dispatched` attempt. A later scheduler therefore
records `Unacknowledged`, never a definite trap or instruction exhaustion.

The registry alone constructs `TimerSnapshot`. Consumers cannot assemble or
mutate impossible state combinations. Provider handles never appear in a
snapshot.

## Frozen counter vocabulary

All counters are epoch-local and saturating:

| Counter | Meaning |
| --- | --- |
| `schedule_requests` | Validated requests to make or reconcile a declaration active |
| `wakeups_armed` | Provider one-shots armed for ordinary work or a watchdog scheduler |
| `work_dispatched` | Immediate watchdog work one-shots committed by scheduler messages |
| `scheduler_started` | Non-stale watchdog scheduler callbacks accepted by the registry |
| `work_started` | Non-stale ordinary or watchdog work callbacks that entered consumer dispatch |
| `work_completed` | Work callbacks whose completion accounting returned and committed |
| `succeeded` | Successful-work completions |
| `no_work` | Valid no-work completions |
| `retryable_failure` | Expected-failure completions that retain retry eligibility |
| `invariant_failure` | Terminal invariant-failure completions |
| `cancelled` | Logical cancellations that changed authoritative state |
| `stale_wakeups` | Rejected ordinary or scheduler callback generations |
| `stale_work` | Rejected watchdog work generations |
| `coalesced` | Valid demand satisfied without another logical schedule |
| `unacknowledged` | Older committed watchdog dispatches retired without committed completion |

Total actual provider arms are `wakeups_armed + work_dispatched`. The Canic
projection maps its existing schedule count to committed `wakeups_armed`,
execution count to `work_started`, and completed performance count to
`work_completed`. `schedule_requests` remains an additional demand signal and
must not replace the legacy committed-arm meaning.

The completion partition remains:

```text
work_completed = succeeded + no_work + retryable_failure + invariant_failure
```

There is deliberately no arithmetic invariant between `work_started` and
`unacknowledged`. A synchronous start mutation can roll back with trapped work,
while the prior scheduler's `work_dispatched` fact remains committed.

## Measurements and runtime epoch

Instruction aggregates are split by callback role:

- scheduler instructions; and
- normally completed consumer-work instructions.

Each has sample count, saturating total, latest, and maximum. A trap or
instruction exhaustion has no end sample and never creates a synthetic zero.
Native/mock execution reports measurement unavailable.

Elapsed IC time is removed from the 0.3 live contract. `ic0.time()` is message
time and does not truthfully measure elapsed duration within synchronous
consumer work. A future provider may add a distinct measured-duration source
through a later reviewed API.

The runtime creates its own observation scope from system facts:

```text
TimerEpoch = { canister_version, started_at_ns }
```

Consumers do not choose or persist an epoch. `canister_version` distinguishes
install/upgrade Wasm instances and `started_at_ns` records initialization time.

## Lifecycle seam

`initialize_runtime` is synchronous and idempotent within one Wasm heap. The
first caller creates the epoch and empty registry; later calls return the same
epoch and never clear registrations contributed by another framework.

The existing lifecycle export owner then invokes synchronous participants.
Each participant derives desired timers from its own durable authority,
registers absent declarations in the fresh post-upgrade heap, and reconciles
them active or inactive before deferred application work.

All three lifecycle reconciliation helpers register retained declarations,
including a fresh inactive declaration. Inactive fixed declarations therefore
remain visible in the bounded inventory, reserve capacity before application
hooks, and report no fabricated generation or provider arm. Transient
`RemoveWhenStopped` declarations use direct registration instead; this
retained-only constraint supersedes the earlier public lifetime parameter.

The crate exports no `init`, `post_upgrade`, or macro. If Canic and IcyDB are
linked through the same Cargo package ID, Cargo unification gives both the same
registry static. Multiple resolved `ic-timers` package IDs create multiple
registries and fail the downstream adoption gate.

## Provider source audit

The provider remains exact `ic-cdk-timers` 1.0.0. The reviewed source hashes
are:

| Source | SHA-256 |
| --- | --- |
| `src/global_timer.rs` | `a060a856318d8d93b43c83179262a40e6abdd83618617d6956e45ed80aefe1d6` |
| `src/timer_executor.rs` | `c33198d5f01cdcd71af987ea561f47b1516e81d27f4e6409262feca8be147a65` |
| `src/lib.rs` | `02e2477206e95b21e7b6506682cbe826251e7cd1835ad1e5b4700873055a4700` |
| `src/state.rs` | `9fe9980707f870331d5053c7d4610a8694c2c43404070fde4684308439854145` |

The source establishes:

- `set_timer` installs a one-shot task and deadline in current heap state and
  performs no immediate self-call;
- the global timer later dispatches the task through the private
  `<ic-cdk internal> timer_executor` self-call;
- external callers are rejected unless caller equals canister self;
- insufficient liquid cycles retain the due timer for a later global-timer
  attempt;
- the global outstanding-call cap is 250 and counts provider dispatch
  self-calls canister-wide rather than `ic-timers` registry handles;
- serial intervals reschedule before callback work but replay overdue
  historical deadlines until provider guards intervene; and
- all provider task/handle state disappears on upgrade.

Therefore the proposed scheduler can register its successor first and its
zero-delay work second, then return to commit both before either later message
runs. If either registration or later scheduler logic traps, the whole
scheduler message rolls back; the production scheduler must consequently have
only checked bounded operations and no consumer call.

Runtime system facts and instruction counters will use a direct exact
`ic0` 1.1.0 dependency behind `platform`. It is already resolved through the
provider, exposes safe wrappers for `time`, `canister_version`, and
`performance_counter`, and has Rust 1.88 metadata. Adding full `ic-cdk` to the
published library is unnecessary.

## Rust 1.88 baseline

The current 0.2.0 code and complete resolved normal dependency graph compile
on Rust 1.88.0 for both native and `wasm32-unknown-unknown` when only the
repository's declared Rust 1.91 metadata gate is ignored. No language,
standard-library, or dependency failure was observed.

The declared 0.3 MSRV is therefore lowered to Rust 1.88.0 in this patch. The
development toolchain remains Rust 1.97.1. Every implementation patch must run
the native MSRV check; patches that change runtime/platform code also run the
Wasm MSRV check.

## Frozen measurement subjects

Patch 3 adds one small PocketIC runtime-probe canister with mutually exclusive
build cohorts sharing the same endpoints and observation DTO:

1. `baseline`: lifecycle and observation endpoints with no timer registered;
2. `once`: one retained no-op `Once` registration;
3. `after-completion`: one retained one-second no-op recurrence; and
4. `watchdog`: one retained one-second two-message no-op watchdog.

Each cohort is built with the same pinned Rust toolchain, Wasm target, Cargo
release profile, and post-link tool versions. Reports record compiler Wasm and
final Wasm raw byte count plus SHA-256. Raw non-gzipped final Wasm is primary;
deterministic gzip is secondary. Deltas are reported against `baseline`, with
`watchdog - after-completion` isolating the stronger scheduling protocol.

The probe records `performance_counter(1)` deltas for:

- initial ensure and first provider arm;
- duplicate ensure/coalescing;
- an accepted ordinary work wrapper;
- an accepted watchdog scheduler;
- an accepted no-op watchdog work wrapper and completion;
- stale scheduler and stale work no-ops;
- unacknowledged-attempt retirement;
- terminal cancellation;
- one snapshot lookup; and
- a full 64-entry deterministic inventory snapshot.

PocketIC reports end-to-end message instructions separately where available,
including provider dispatch. No fixed ceiling is invented before the first
local measurements. Every later patch reports absolute values and deltas from
the preceding accepted patch using these unchanged subjects.

Cycles are reported separately for the additional watchdog scheduler self-call
when the test environment exposes a stable measurement. Instruction and cycle
costs are never conflated.

## Patch 6 measurement adjustment

The final mutually exclusive cohorts live in a dedicated `testing/size-probe`
rather than the recovery probe so adversarial endpoints cannot perturb the
size subjects. Callback tokens remain private and there is no public executor,
so isolated stale scheduler/work messages cannot be invoked in PocketIC
without introducing a forbidden alternate ingress route. Stale generations
remain directly injected in owner-local native tests and receive no fabricated
IC instruction value. The full 64-entry inventory is measured in the separate
recovery probe for the same non-contamination reason.

All other frozen subjects are reported with raw compiler/final Wasm hashes,
instruction deltas, and PocketIC cycle observations in the
[0.3 runtime evidence report](../audits/0.3-runtime-evidence-2026-08-13.md).
