# Registration continuity and Watchdog deadlines

Status: implemented in the tagged 0.8.0 release; registry publication not verified here.

## Owner feedback

Canic's CANIC-002 cost-evidence handoff requires registration continuity before
it can subtract timer counters. A runtime epoch alone cannot distinguish an
unregister/re-register cycle followed by counter regrowth. Toko Miner's
2026-09-20 checkpoint qualification also uses an auxiliary Once registration
solely to wake its Watchdog at the next application-owned deadline.

Both changes belong in the existing registry. No second counter owner,
scheduler, durable state, provider path or consumer-specific dependency is added.

## Inert registration identity

`TimerSnapshot::registration_id()` returns `TimerRegistrationId`, containing the
runtime `TimerEpoch` and a nonzero `sequence()`. The registry projects its existing
checked claim generation; it does not allocate another identity counter. The
value has no public constructor, does not expose a provider handle, and is never
accepted by a control operation.

The identity remains stable across scheduling, cancellation, stop/resume, callback
completion, trapped work and instruction exhaustion. Removing and registering
the same structured identity again allocates a different sequence and fresh
counters. Runtime reconstruction starts a new epoch, even when registration
sequences repeat. Sequence exhaustion returns `RegisterError::ClaimGenerationExhausted`
without wrapping, inserting an entry or resetting an existing registration.
There is no independent counter-reset operation.

The identifier is scoped to one canister's runtime history. Consumers must retain
canister identity and reject observations across reinstalls or restored/forked
histories; it is not a globally authenticated execution receipt. Callback
`generation()` remains a scheduling observation, never a counter-continuity key.

For a cumulative field, interval arithmetic requires:

1. the same canister, registration identifier and metric role;
2. ordered, fresh observations with advancing source times and compatible windows;
3. neither endpoint at `u64::MAX`, and no counter decrease.

Counters and instruction sample counts/totals saturate independently. An endpoint
at `u64::MAX` is conservatively unavailable for exact subtraction, even if it was
reached exactly. Latest/maximum measurements and memory extents are not cumulative
counters. Trapped/exhausted work commits no start/completion/sample mutation; a
later scheduler can record an unacknowledged attempt. Continuity does not turn
those missing samples into zero or recover complete-message instructions.

Canic can carry the epoch and sequence through its existing DTO/metric owner and
use them to qualify deltas. Funding-transfer completeness, aligned balance
windows and actual cost attribution remain separate owners. This change does not
establish callback rates, billed cycles or downstream savings by itself.

## Exact Watchdog scheduling

The public additions are:

- `WatchdogRegistration::reconcile_schedule(Option<TimerSchedule>)`;
- `WatchdogContext::reconcile_schedule(Option<TimerSchedule>)`;
- `WatchdogDecision::ScheduleAt(u64)`; and
- `WatchdogReconcileState::ScheduledAt(u64)`.

`TimerSchedule::At` preserves the exact timestamp; a past timestamp arms a
zero-delay later message. `After` resolves once at request time using checked
nanosecond arithmetic. Invalid relative durations or overflow return typed errors
before changing the schedule. `None` cancels through the same handle-custody path
as explicit cancellation, including removal of transient registrations.

| Current state | Exact reconciliation |
| --- | --- |
| Inactive | Arm one scheduler at the requested deadline. |
| Scheduled, different deadline | Replace the owned wake-up, earlier or later, and rotate the callback generation. |
| Scheduled, identical deadline | Coalesce and retain the actual scheduling mode and armed delay. |
| Work dispatched | Keep queued work and the committed cadence wake-up; retain one pending proposal for that attempt's normal completion. |
| Work running | Retain one pending proposal for normal completion; do not alter the committed recovery wake-up inside consumer work. |

Normal `ScheduleAt` completion replaces the exact pre-armed successor. An equal
successor deadline needs no provider call. The next scheduler still pre-arms
`dispatch time + cadence` before separately queuing work. Cadence is therefore the
recovery retry interval, not the deadline of every successful continuation.
An interruption leaves the committed cadence successor; recovery retires the
interrupted attempt and its pending proposal. Consumers must rederive demand from
their durable authority and keep work bounded and idempotent.

One existing pending command arbitrates all requests. Invariant failure always
stops; unregister is sticky. Later cancellation wins, while later exact
reconciliation or ensure can re-enable a pending cancellation. Exact
reconciliation supersedes earlier scheduling proposals, including immediate ones.
A subsequent cadence ensure retains a pending exact deadline; running immediate
ensure advances a future pending deadline but retains an already earlier one.
Immediate/cadence ensures during the dispatched gap still coalesce with the
already queued work. Pending commands override the returned decision.

Absolute schedules project `Deadline`, no requested relative delay, and the
actual nonnegative armed delay. Relative reconciliation uses the existing `Once`
scheduling-reason label; policy remains `Watchdog`. Scheduler dispatch returns
the effective reason to `Watchdog`. No snapshot state variant, registry capacity
or at-most-two provider-handle bound changes.

## Release and adoption

The snapshot shape and exhaustive Watchdog enums change on the 0.8 minor line.
There is one current snapshot/API shape, without a compatibility alias, dual
reader or legacy feature. The local Canic-shaped projection and probe DTOs carry
the registration identity in the same change.

Canic, IcyDB and applications must coordinate one resolved `ic-timers` package
identity when adopting the release. For Toko Miner, replace the auxiliary
checkpoint-deadline registration with this Watchdog's exact schedule in one
hard cut; retain the application-owned deadline calculation and lifecycle
reconstruction. Downstream repositories remain read-only in this task. Their
actual adapters, combined-Wasm qualification and controlled cost comparison are
not claimed here.

## Evidence

The maintained native tests cover registration replacement and counter regrowth,
epoch changes, sequence exhaustion, cancellation, deadline movement/coalescing,
stale delivery, pending precedence, expired contexts, invalid durations and
callback-generation exhaustion. The existing counter tests enforce saturation.
The real-Wasm PocketIC matrix covers deadline sleeping/replacement, identity
continuity through explicit trap and recovery, reset on upgrade, and replacement
followed by counters growing beyond the earlier sample. Explicit trap and actual
40-billion-instruction exhaustion occur after a nested future-deadline proposal;
the original cadence recovery wake-up survives both.
