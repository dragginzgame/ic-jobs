# 0.26 independently implemented timer backend

Status: released as 0.26.0, 2026-10-16 (local tag `v0.26.0`, commit `9c84824`;
publication confirmed by the maintainer). The old provider has been removed.
Qualification is source-bound and recorded in the [handoff](../../status/current.md).
The candidate receipts below used the earlier 0.25.2 package identity; they remain
historical evidence. Published-version downstream adoption and the recorded
qualification gaps remain separate work.

## Decision and purpose

Replace `ic-cdk-timers` with an independently authored, private one-shot backend
inside IC Timers. Retain the established async executor and IC system bindings.
Own scheduling, cancellation storage and dispatch behavior so improvements can
be qualified alongside the runtime that uses them.

This is an ownership decision, not a finding that upstream is abandoned. The
upstream repository remains active; timer-specific development and review have
been slow. Neither a smaller dependency graph nor faster execution is promised.
Only measurements of the completed implementation can establish improvements.

The captured before-image baseline is Cargo 0.25.2, `ic-cdk-timers` 1.0.0, executor 2.0.0 and
`ic0` 1.2.0. Freeze the actual source, lockfile and compiler at implementation
start; this document is not a reusable qualification receipt.

## Independent authorship and licensing

Keep repository-owned code under MIT. Implement from the
[IC system API specification](https://docs.internetcomputer.org/references/ic-interface-spec/canister-interface/),
our current public contracts and our own tests. Do not copy or closely translate
upstream source, comments, tests or module structure. Record the requirements
and provenance of the implementation in its review.

The preceding audit inspected upstream source. This proposal therefore does not
claim strict clean-room development. A strict clean-room process would require
an implementation author isolated from that source and supplied only a reviewed
behavioral specification. Renaming or mechanically restructuring upstream code
does not establish independent authorship. If implementation requires adapted
upstream expression, stop treating that portion as MIT-only and resolve its
Apache-2.0 attribution and distribution obligations before incorporating it.

Retained dependencies keep their own licenses and distribution requirements.
Independent implementation is not a patent-clearance claim. The copyright
distinction between expression and methods is described by the
[U.S. Copyright Office](https://www.copyright.gov/help/faq/faq-protect.html).

## Scope and ownership

| --- | --- |

Keep `Once`, after-completion and synchronous Watchdog public APIs unless concrete
implementation evidence requires a separately documented change. Preserve inert
snapshots and non-exported handles. Do not introduce a second registration or
recurrence authority, public low-level timer API, handler registry or storage layer.

Remove `ic-cdk-timers` entirely from the selected dependency graph at cutover.
Declare the retained executor in the root dependency catalog and inherit it in
the member manifest. Do not rewrite the executor, import upstream interval
support or add a compatibility provider feature. Dependency selection changes
need their own recorded graph evidence; retain existing versions where possible.

## Backend design

### Armed tasks and deadlines

Use a private store of one-shot tasks with checked, non-reusable stale identities.
Start with a bounded slot store and an earliest-deadline scan: the runtime already
bounds registrations and owned handles, so an additional heap and lazy cancelled
records need measured justification. Specify a deterministic tie order.

Derive capacity from actual handle lifetimes, including detached/replacement and
in-flight dispatch states; do not assume the public 128-owned-handle bound is the
complete peak allocation bound. Admission exhaustion returns a typed failure
before publishing scheduling authority. Reuse an existing appropriate error or
add a documented public variant only when required by the failure contract.

Cancellation removes the armed task and deadline immediately. Drop captured
futures after releasing internal borrows, because their destructors can inspect
or control runtime state. Cancellation of already accepted running work must
retain the current public contract; it must not silently become future abortion.
Transport callbacks refer to checked identities, never a reusable slot alone.

Keep absolute deadline arithmetic checked, preserve zero-delay eligibility and
account for the IC's zero timestamp meaning timer deactivation. Arm the earliest
eligible deadline and deactivate when nothing remains. Rearm after timer entry,
queue mutation and transport retry as appropriate. A cached deadline must not
prevent rearming after the IC consumes its timer.

This design bounds armed queue records, not future captures, executor allocations,
all in-flight work or total canister memory. State each resource bound separately.

### Message boundaries and transport

The global-timer message selects due work and dispatches authenticated self-calls.
Consumer work runs in separate messages. Do not poll consumer futures directly
inside the global-timer dispatcher or combine Watchdog scheduling with its work.
The Watchdog scheduler must commit its successor before consumer work starts.

The internal endpoint accepts only self-originated calls, validates exact payload
shape and task identity, and treats obsolete delivery as harmless. Define reply,
reject and cleanup ownership for each transport allocation. Release each exactly
once on successful completion, submission failure or cleanup; review rollback
behavior rather than treating native panic handling as IC trap recovery.

Keep awaiting ordinary callbacks integrated with the supported executor context.
Preserve abandonment handling both before the first await and after a continuation
trap. Watchdog work remains synchronous. Consumer-spawned async delivery must also
be qualified against the selected executor and endpoint response lifetime.

Explicitly define the state transitions from armed to submitted to accepted and
completed, including cancellation at each boundary. A submission failure leaves
work eligible for later dispatch. A timeout or transient rejection is not proof
that work never executed: retry transport only while the same task remains
eligible, and validate identity again at acceptance. Never infer permission to
repeat an application effect from a lost transport response.

Bound outstanding self-calls and work per global-timer invocation. Preserve a
retry opportunity when dispatch cannot proceed, without dropping due work or
spinning inside one invocation. Specify low-cycle retry delay, transient retry
delay and fairness before coding them; these are measured backend policies,
not durable job retry policy. Start conservatively and avoid tuning multiple
policies while establishing the recovery baseline.

### Exports and unsafe code

Use directory modules under `platform/`; keep all authority crate-private.
Prefer supported executor/CDK interfaces where they preserve the required message
and cleanup contracts. Direct exports and raw IC callbacks require explicit unsafe
review and cannot be hidden beneath the current crate-wide `forbid(unsafe_code)`.

The preferred packaging is one published crate, with a narrowly scoped FFI module:
retain unsafe prohibition in the safe modules, deny unsafe by default, and allow
only the reviewed boundary. Every unsafe operation needs a written ownership and
rollback invariant. Implementation review selected that narrow boundary:
`ffi.rs` contains IC exports and callback registration, with no pointer casts or
raw allocation ownership. Other runtime modules forbid unsafe code; the root
and workspace deny it by default. The live boundary checker enforces confinement.
The native test substitute never changes production admission or dispatch.

The final Wasm must have one global-timer owner and one intended internal executor
endpoint. Inventory all direct and transitive timer users in adopting canisters;
reject coexistence with the old provider. Review a Cargo `links` guard or equivalent
build-time ownership check, and verify actual final-Wasm exports. Multiple versions
of IC Timers must not silently create independent active runtimes.

### Selected implementation decisions

The pending queue uses a compact vector and scans at most 130 records, ordered
by deadline and then monotonically allocated task identity. Cancellation removes
the entire record immediately. Capacity is an independent admission bound:
128 owned roles plus two transition slots; detached ownership does not duplicate
a task, and accepted running work leaves the pending queue. No unlimited transient
allocation is assumed: capacity and identity exhaustion return typed errors and
use the existing failed-binding retirement path. This does not preserve a false
scheduled registration after failed admission.

A separate 128-slot table owns outstanding dispatch contexts. Callback environments
are table indices. The table never reuses an occupied slot; the IC delivers a
response once or invokes cleanup after rolling back a trapped response. Cleanup
therefore sees the restored original table entry. The context is taken before
entering the executor callback/recovery API. Submission rejection releases its
slot locally. All allocations occur before checking liquid cycles for submission.

The unpublished ordinary probe deliberately traps a callback capture destructor
after pre-await work traps. PocketIC verifies that response rollback plus cleanup
preserves the pending registration, defers its retry by one second, and then
retires it when the destructor trap is disabled. Both ordinary policies and a
subsequent independent timer are covered. This fault exceeds the supported
nontrapping-destructor contract; it does not establish arbitrary destructor-trap
recovery or transport-table saturation.

The unpublished transport probe fills the IC self-call queue with CDK calls and
replenishes them on reply. It observes actual `CallPerformFailed` results while
keeping ample cycles available. The timer remains pending after pressure drains,
then dispatches once after the one-second retry delay. Given one pending timer,
no accepted timer dispatch and ample cycles, this delay exercises the backend's
nonzero `call_perform` branch by source-level inference; there is no injected
result or production branch counter. The [IC system API contract](https://docs.internetcomputer.org/references/ic-interface-spec/canister-interface/)
specifies that failed submission schedules no callback. This qualifies recovery
under the recorded queue pressure, not saturation of the backend's 128 contexts.

The deferred-control subject cancels or replaces the pending registration under
the same real queue pressure. After pressure drains, an authenticated self-call
using the removed backend identity cannot revive it. Passing the retry deadline
leaves cancelled work stopped and runs replacement work once; the retained
cancelled registration can then be scheduled again. Cancellation removes only
pending ownership: outstanding transport slots remain owned until their terminal
callback, preventing slot reuse while a response can still arrive.

The dispatcher processes at most 128 tasks per invocation. Submission failure,
insufficient liquid cycles or occupied transport capacity sets a one-second
canister-wide dispatch delay. Reject codes 2 and 6 requeue only the still-pending
identity after one second; other responses retire any remaining task. Acceptance
consumes the identity before polling consumer code. Late replies and repeated
requests cannot resurrect an accepted or cancelled task. Deadlines use saturating
retry addition at the timestamp ceiling; ordinary admission arithmetic is checked.
The internal endpoint is `<ic-timers internal> dispatch`, with an exact eight-byte
little-endian identity and self-caller authentication.

Cargo's `links = "ic-timers-global-timer"` rejects multiple packages declaring
that key. Older Timers releases lack it, so Cargo alone cannot reject every mixed
generation or other provider. Graph, global-timer export collision and final-Wasm
checks remain necessary. No provider compatibility alias is kept.
The endpoint exports no Candid interface or application lifecycle hook.

## Contracts preserved and deliberately retired

Preserve registration atomicity, typed validation, stale-delivery rejection,
callback-scoped authority, ordinary awaiting, Watchdog successor isolation and
synchronous lifecycle reconstruction. Keep the recovery limitations in
[SAFETY.md](../../../crates/ic-timers/SAFETY.md), including scheduler normal-return assumptions and
application idempotency. No exactly-once or guaranteed punctual-delivery claim.

Retire the provider dependency, provider handle representation, old internal
executor endpoint assumptions, provider-specific boundary checker and claims
that only the CDK owns timer dispatch. Replace checks with live architectural
invariants. Update AGENTS.md, README, Rustdoc, architecture, safety, release
qualification guidance and probes together. Preserve historical changelogs and
source-bound evidence as history, not current proof.

There is one production backend after the cut: no feature flag, dual scheduling,
fallback, compatibility alias or retained legacy implementation. Existing timers
remain volatile and reconstruct from application authority on upgrade. This cut
does not require resetting durable application or Jobs records. An operational
rollback uses a reviewed previous artifact and normal lifecycle reconstruction,
not a second backend compiled into the new runtime.

## IC Jobs and downstream adoption

IC Jobs core remains a timer-independent state-transition library. Its consumer
owns storage, due-time indexing, bounded dispatch and direct Timers integration.
No new Jobs runtime dependency, lifecycle export or automatic retry of uncertain
effects belongs in this change.

Qualify the Jobs consumer's deadline replacement, pause/resume, idle behavior,
watchdog batch rollback, async delivery and receipt reconciliation on the new
Timers package. Its current consumer is bounded to 32 jobs and is not proof of
large-queue throughput. Use it as an end-to-end measurement subject, separating
timer cost from storage and external-call costs. Any fairness or larger-queue
Jobs work requires its own concrete consumer requirement.

Adoption must resolve one Timers package ID and remove any direct provider use
atomically. Review Canic, IcyDB and actual composed canister graphs as well as Jobs;
this document does not authorize mutation of sibling repositories. Record exact
consumer versions and final-Wasm evidence when adoption is performed.

## Implementation sequence and review gates

1. Freeze the baseline and requirements. Capture source/lock/toolchain identities,
   existing recovery subjects and four policy cohorts. Resolve admission capacity,
   transport state transitions, retry constants, endpoint naming and the scoped
   unsafe policy in this document before implementing that boundary.
2. Implement the independently authored task store and deadline selection. Test
   the production data structure natively, including overflow, exhaustion,
   immediate cancellation, equal deadlines and reentrant capture destruction.
3. Implement IC entrypoints and executor integration. Add focused real-Wasm
   transport subjects before claiming callback recovery. Review unsafe ownership,
   authenticated admission, cancellation races and timeout ambiguity together.
4. Connect the runtime and remove the old backend in the same coherent cut.
   Propagate fallible admission through binding rollback and registration cleanup.
   Update manifests, lock graph, boundary checks, documentation and probes.
5. Qualify behavior and costs, then prepare consumer adoption. Record failures and
   limitations alongside successful receipts. Update pending release notes to
   describe implemented behavior rather than this plan. Release remains user-run.

Implementation checkpoints are review steps, not independently supported modes.
Native fake-platform tests remain useful for policy but do not qualify backend
execution. No old-provider compatibility path is part of a completed checkpoint.

receipts cannot qualify this implementation. Performance acceptance means no
