## Objective

Turn the current value/control-model foundation into the smallest
production-grade timer runtime that IcyDB can safely adopt for its startup
recovery watchdog, while remaining suitable as the shared timer authority for
Canic and application timers.

The central invariant is:

> The next watchdog wake-up is committed before fallible consumer work begins.

A normal after-completion callback is not sufficient. A provider interval is
not automatically sufficient merely because it repeats.

## Frozen IcyDB contract

The replacement must preserve these downstream properties:

1. A fixed one-second startup recovery watchdog can be registered
   synchronously during `init` and `post_upgrade` whenever IcyDB's durable
   readiness authority reports pending recovery.
2. A future wake-up survives a trap or instruction exhaustion in the later
   consumer-work message. This guarantee does not cover the scheduler message.
3. At most one recovery page is accepted for one timer cadence generation.
4. Duplicate, stale, late, and overlapping callbacks are harmless.
5. Terminal readiness or durable startup failure cancels the watchdog safely.
6. Timers lost during upgrade are reconstructed before downstream
   post-upgrade hooks.
7. A normally returned mutation error that retained recovery controls can
   synchronously and idempotently ensure a future wake-up before returning.
8. Timer delay, insufficient cycles, traps, and instruction exhaustion are
   retryable operational conditions, not durable database corruption.
9. Consumer work has no externally invokable executor route.
10. IcyDB retains sole durable readiness and startup-failure authority.
    `ic-timers` neither persists nor invents database authority.

The IcyDB adapter must use the following exact returned-result mapping. A work
unit is one bounded recovery page or generated-schema handoff that returned
normally; an observation made before doing such work reports zero units.

| IcyDB result | `TimerCompletion` | `WatchdogDecision` |
| --- | --- | --- |
| Recovery remains pending after one normally completed unit | `success(1)` | `Continue` |
| A normally returned retryable execution failure | `retryable_failure(completed_units)` | `Continue` |
| `Ready` observed before doing work | `no_work()` | `Stop` |
| `Ready` reached by normally completed work | `success(completed_units)` | `Stop` |
| Durable terminal database failure | `invariant_failure(completed_units)` | `Stop` |

`completed_units` is normally zero or one for the bounded startup callback.
Trap and instruction exhaustion return no result and therefore commit no
completion. A later scheduler may record only an unacknowledged dispatch.

## Canonical runtime ownership

Version 0.3 adds one bounded canister-local registry. It is the sole live
authority for:

- declared timer identities and configured policies;
- policy-specific volatile control state;
- every live provider handle;
- callback generations and stale-callback arbitration;
- live epoch-scoped observations; and
- erased consumer callback ownership.

The registry has a fixed capacity chosen and documented during the inventory
patch. Capacity exhaustion is a typed error and does not partially register a
timer. Identities retain the bounded deterministic `owner/subsystem/name`
shape. Each identity has one canonical claimant and one entry.

Provider handles are linear implementation details: the public API must not
expose, clone, or copy them. Cancellation clears the actual handles owned by
the entry. Snapshots remain inert observations and cannot be used to mutate
the registry.

`TimerControl` may remain the internal state machine for `Once` and
`AfterCompletion` if its state is truthful for those policies. Watchdog state
must use a separate policy-specific machine because it simultaneously owns a
scheduled successor and an outstanding work attempt. Do not distort a single
`Scheduled | Running` registration into representing both facts.

All publicly retained policies must be implemented and tested in this line:

- `Once`;
- `AfterCompletion`; and
- `Watchdog`.

Remove or hard-cut any policy, directive, or snapshot shape that remains
aspirational.

## Trap-safe watchdog protocol

The watchdog uses one-shot provider timers and two distinct callback messages:

1. A small scheduler callback validates the timer identity and scheduler
   generation.
2. Using the scheduler message's current IC time, it computes one checked
   successor deadline at `now + cadence`.
3. It arms that successor and enqueues a separate zero-delay work callback.
4. It records the dispatched work attempt and returns without invoking
   consumer code.
5. Returning commits the successor, work callback, and registry transition
   before the work callback can execute.
6. The later work callback validates its identity and attempt generation,
   releases all registry borrows, and invokes synchronous consumer work with
   no `await`.
7. Normal return records the supplied completion and either retains the
   pre-armed successor or terminates and clears it.
8. A trap or instruction exhaustion rolls back the work message but does not
   roll back the successor committed by the scheduler message.
9. When the successor observes an older dispatched attempt without a committed
   completion, it retires that attempt, records it as unacknowledged, makes
   late work stale, and dispatches the new cadence attempt.
10. Stale scheduler and work callbacks are bounded no-ops.

The successor is scheduled relative to the current scheduler dispatch time,
not a missed historical deadline. A large time jump therefore produces one
new cadence point rather than replaying every missed interval.

The scheduler path performs only bounded registry arbitration, checked
generation/deadline work, and two provider registrations. It cannot invoke
consumer work, build an inventory snapshot, or run an unbounded loop. Positive
cadence and initially requested deadlines are validated before registration;
runtime generation and deadline exhaustion are handled as typed terminal
control failures rather than explicit production panics.

Cancellation allocates no callback identity. It makes scheduled or dispatched
work inactive and clears the selected handles, or queues a stop for running
work's normal completion. Inactive state rejects old deliveries; later arming
and dispatch allocate fresh checked generations. Cancellation therefore remains
available at exhausted counters, while creating a new callback still fails.
The [0.11.0 note](../changelog/0.11.0.md) records this semantic hard cut and its
pending verification; it does not extend the historical recovery evidence.

The pinned provider's one-shot registration mutates canister heap state and
the global-timer deadline in the current message. The protocol depends on the
scheduler returning normally so those actions commit before the later work
timer message. PocketIC must prove this exact boundary. If real-canister
evidence disproves it, stop and document the failure before selecting another
mechanism. Do not ship two watchdog protocols.

The trap/exhaustion recovery claim is intentionally asymmetric. The scheduler
message itself has no pre-armed replacement for the successor it is about to
create. It is therefore kept fixed and bounded, cannot invoke consumer work,
and has no explicit production panic or unhandled recoverable branch; a trap
or exhaustion in that scheduler message is outside the demonstrated recovery
guarantee.

IcyDB's accepted 0.225 implementation currently uses the provider-native
serial interval. Its maintained evidence proves successor survival, but a
five-minute jump can still dispatch the provider's 250-call shared cap at one
IC time; IcyDB needs an additional cadence-time guard to make all but one
recovery attempt cheap. Version 0.3 deliberately replaces that mechanism with
one one-shot protocol scheduled from actual dispatch time, so missed cadence
points coalesce before dispatch rather than merely becoming guarded no-ops.

## Registry and public API requirements

Expose the smallest coherent API needed to:

- register one deterministic identity, implemented policy, and callback;
- synchronously and idempotently ensure a declared timer is scheduled;
- cancel or unregister it through its canonical registry ownership;
- reconcile desired live state during ordinary operation;
- reconstruct declarations and desired scheduling during `init` and
  `post_upgrade`;
- obtain one bounded, deterministically ordered coherent inventory;
- obtain one timer snapshot or functional failure streak by identity; and
- dispatch internal generation-checked scheduler and work callbacks.

The API must define, with focused tests:

- registration ownership and the difference between an idempotent repeat and
  a conflicting duplicate;
- whether a stopped declaration remains available for a later
  `ensure_scheduled` call;
- policy-specific legal completion/directive combinations;
- nested `ensure_scheduled` and cancellation invoked by consumer work;
- cancellation of a successor that has already been dispatched but not yet
  accepted;
- replacement and stale behavior for every owned provider handle;
- checked positive cadence and deadline arithmetic; and
- capacity exhaustion without partial state or leaked handles.

No registry borrow may be held while consumer work executes or awaits. The
production scheduler and registry paths contain no explicit `panic!`,
`unwrap`, or `expect`, and no recoverable error is silently discarded.

## Lifecycle integration

Provide a synchronous, idempotent runtime-initialization and reconstruction
seam that one existing lifecycle export owner calls during `init` and
`post_upgrade`, before application hooks or deferred work.

The seam does not own lifecycle exports. Consumers derive desired live timers
from their existing durable authority, declare them, and request scheduling.
They do not persist timer handles, generations, policies, callbacks, or an
epoch solely for recovery.

When IcyDB, Canic, and an application resolve to the same Cargo package ID for
`ic-timers`, they use the same library static and therefore the same registry.
Resolving multiple `ic-timers` versions would create multiple registries and
is unsupported; downstream adoption must check dependency unification.

That check must inspect the final canister graph, not only one library crate,
and must inventory every remaining direct `ic-cdk-timers` dependency and call.
The provider's 250 outstanding-dispatch limit is canister-wide. The registry's
maximum of 128 owned handles bounds `ic-timers` state but does not reserve 128
of those calls or prove headroom when other direct timer users are linked.
Remaining direct users must either migrate to the shared registry or be named
as deliberate fixture-only exceptions before adoption.

## IcyDB-shaped fixture

Add an internal fixture that models only IcyDB's timer contract:

- one fixed identity;
- a one-second `Watchdog` policy;
- one synchronous bounded page of work;
- consumer-supplied `Ready`, `Recovering`, or terminal-failure observation;
- the exact progress, returned retryable failure, Ready, and durable terminal
  mapping frozen above;
- a synchronous `ensure_scheduled` call representing the returned-error
  commit-guard path; and
- no query-side driver or public executor.

Do not copy database, journal, schema, receipt, or readiness authority from
IcyDB.

## Live observability

The 0.2 snapshot becomes a projection of registry state rather than a set of
freely combinable aspirational values. Construction and mutation must not
permit impossible policy/state/handle combinations.

The two-message watchdog requires explicit observation of scheduler callbacks,
work dispatches, accepted work callbacks, completed work, and unacknowledged
attempts. A future scheduler can prove only that an earlier dispatched attempt
has no committed completion. It cannot prove whether that work trapped,
exhausted instructions, was delayed, or was superseded. Names and docs must not
claim a definite trap or interruption.

Starts and completions remain distinct, but an entry mutation performed inside
a trapping synchronous work message rolls back. The committed pre-work
`dispatched` fact is therefore the durable-in-epoch basis for detecting an
unacknowledged attempt; do not relabel a dispatch as a callback start.

Define whether `armed` counts scheduler and work one-shots together or expose
separate counters so provider effects remain interpretable. Completion classes
remain success, no work, retryable failure, and invariant failure. Cancellation,
stale callbacks, coalescing, and unacknowledged work remain separate events.
All hot-path counters saturate.

Measure instructions only where the IC exposes a truthful start/end delta.
For synchronous work, IC time is message time rather than a meaningful elapsed
duration; omit elapsed duration from the 0.3 live contract instead of recording
a fabricated zero. Missing completion still produces no synthetic performance
sample.

- work instruction exhaustion with successor survival;

- canister stop and resume;
- insufficient cycles, top-up, and eventual progress;

## Initial design review

The direction is accepted for planning, with these decisions required in
Patch 1 before runtime mutation:

1. Hard-cut the flat 0.2 state shape into policy-specific valid states. In
   particular, watchdog successor and outstanding attempt cannot be encoded as
   `Running` plus an optional decorative successor.
2. Make `platform` and its handle private. The current public `set_timer`,
   `clear_timer`, and copyable handle would remain a second provider path and
   violate linear ownership.
3. Add a committed `work_dispatched` fact and an `unacknowledged` outcome or
   event. The current `Interrupted` name is too strong for delayed or
   superseded work, and a `started` increment inside trapping work does not
   survive rollback.
4. Freeze the registration capability and duplicate-owner rule. Callback
   closures cannot be compared for equality, so "idempotent registration"
   must not silently let an unrelated duplicate replace or believe it owns the
   first callback.
5. Freeze the policy/directive matrix. The IcyDB watchdog needs only
   `Continue` and `Stop`; ordinary Canic timers need richer retry,
   continuation, deadline, and after-completion decisions.
6. Retain stopped declarations, or provide an equally explicit mechanism, so
   IcyDB's later normally returned commit error can re-enable its watchdog
   synchronously without reconstructing callback authority.
7. Split or precisely define provider-arm counters because one watchdog
   cadence now arms both a successor and a work callback.
8. Remove elapsed nanoseconds from the live 0.3 contract. IC message time does
   not measure synchronous callback duration.
9. Freeze the registry capacity and comparable Wasm/instruction baselines from
   maintained consumer inventories before choosing numeric gates.
10. Measure the deliberate cost of the stronger boundary. The protocol adds a
    scheduler callback message and therefore one extra provider self-call per
    cadence compared with the current serial interval; raw Wasm, instructions,
    and cycles must make that tradeoff visible.

These are refinements of the proposed protocol, not reasons to reject it. The
two-message boundary is the correct center of the 0.3 line.

All ten decisions are resolved by the
[Patch 1 runtime contract](0.3-patch-1-contract.md). Later changes require
concrete implementation or real-canister evidence and an explicit contract
update.

## Patch 2 implementation boundary

Patch 2 implements the closed value model and pure fixed-capacity registry.
It emits provider-neutral arm, clear, and watchdog-dispatch effects and counts
actual arms only after explicit effect-application confirmation. It does not
store consumer callbacks, own provider handles, install a global registry, or
execute messages. Therefore its watchdog transitions are state-machine
evidence only; at that patch boundary the commit-before-work guarantee remained
unimplemented pending the platform protocol and PocketIC evidence.

## Patch 4 implementation boundary

Patch 4 implements the provider protocol and the public synchronous watchdog
callback surface. Canonical entries own at most one successor handle and one
work handle. Scheduler work is bounded to state arbitration, checked deadline
calculation, and two one-shot registrations; it has no path to the consumer
closure. The initial real-canister probe proves explicit-trap rollback and
successor survival, but it does not yet prove instruction exhaustion, upgrade
reconstruction, insufficient cycles, or the remaining multi-timer matrix.

## Patch 5 implementation boundary

Patch 5 adds synchronous idempotent reconstruction around consumer-owned
volatile registration slots and consumer-supplied desired state. It adds live
instruction deltas for normally completed accepted scheduler/work callbacks
and no synthetic sample for a trap. The owner-local IcyDB-shaped fixture covers
Ready/Recovering/terminal observation and commit-guard re-enablement without
copying database authority. PocketIC now proves scheduled upgrade
reconstruction before a probe downstream-hook observation and subsequent
progress. Instruction-exhaustion, cycles, stop/resume, multi-timer, and
comparable-cohort evidence was reserved for Patch 6.

## Patch 6 closeout boundary

Patch 6 completes the real-canister matrix on PocketIC 15 and Rust 1.88:
explicit trap, 40-billion-instruction exhaustion, provider-executor ingress
rejection, upgrade reconstruction before a downstream-hook observation,
stop/resume, insufficient cycles and top-up, terminal and scheduler/work-gap
cancellation, duplicate demand, two-timer trap isolation, 300-second overdue
coalescing, commit-window ensure, and one-attempt-per-generation observations.

Mutually exclusive baseline, Once, after-completion, and Watchdog cohorts
report compiler and Binaryen-optimized raw Wasm, instruction, and PocketIC
cycle deltas. A separate full-capacity probe measures the deterministic
64-entry inventory without contaminating those size cohorts. Exact commands,
hashes, values, complexity delta, and downstream handoff are in the
[0.3 runtime evidence report](../audits/0.3-runtime-evidence-2026-08-13.md).

The frozen stale-callback instruction subject is deliberately not exposed in
Wasm: callback tokens are private, and adding a benchmark executor would
violate the no-alternate-ingress requirement. Stale generation behavior stays
directly injected in owner-local native tests; no IC measurement is invented.
