# 0.3 runtime evidence — 2026-08-13

## Verdict

The `ic-timers` side of the frozen IcyDB watchdog promotion gate is complete.
The one-shot scheduler commits a cadence successor and a separate immediate
work callback, then returns without invoking consumer work. PocketIC proves the
successor remains authoritative after explicit trap and actual instruction
exhaustion in the later work message.

This began as an implementation and evidence verdict rather than a downstream
adoption claim. The unchanged runtime was subsequently released and published
as 0.3.0. IcyDB and Canic were inspected read-only and still use their existing
timer implementations.

## Canonical ownership and state

- One volatile thread-local runtime owns one `TimerRegistry` for the resolved
  `ic-timers` Cargo package ID.
- The registry contains at most 64 deterministically ordered identities. One
  identity has one opaque claim generation, one configured policy, one erased
  callback, and one coherent policy-specific state.
- An ordinary entry owns zero or one private linear provider handle. A
  watchdog owns zero or one scheduler successor and zero or one immediate work
  handle. No provider handle appears in public API or snapshots.
- `Once` and `AfterCompletion` use `Inactive | Scheduled | Running` ordinary
  state. `Watchdog` uses `Inactive | Scheduled | AwaitingWork`, where
  `AwaitingWork` pairs an authoritative successor with exactly one dispatched
  or running attempt.
- Consumer work runs without a registry borrow. Nested ensure and cancellation
  use the exact delegated claim and commit through the owning state machine.
- The runtime persists nothing. Consumers derive desired scheduling from their
  existing durable authority and reconcile a caller-owned volatile
  registration slot during lifecycle execution.

All direct `ic-cdk-timers` use remains in the private `platform` module. The
published dependency stays pinned to `ic-cdk-timers` 1.0.0; the only new direct
dependency is exact `ic0` 1.1.0, already present transitively, for time,
canister-version, and instruction system facts.

## Real-canister evidence

The tests use PocketIC 15.0.0, Rust 1.88.0, and a one-second watchdog cadence.
The exact PocketIC evidence binary has SHA-256
`29472ea4433b30a280676c4e22e369d79d5ba6ee1b4d48bab32ebe7d0ad2b4bb`.
The release gate now verifies both its version output and hash before running
the suite.

| Required case | Direct evidence |
| --- | --- |
| Work trap | An explicit `ic0.trap` in work leaves the committed successor; the next scheduler records one unacknowledged attempt and later work completes. |
| Work instruction exhaustion | A work callback reaches PocketIC's 40,000,000,000-instruction message limit; it records no completion/sample, while the next cadence later progresses. |
| External executor ingress | An anonymous update to `<ic-cdk internal> timer_executor` is rejected and leaves the snapshot unchanged. |
| Upgrade reconstruction | Probe-owned durable desired bits survive upgrade; `post_upgrade` initializes and reconciles both timers before setting its downstream-hook observation, and later work progresses. |
| Stop/resume and overdue coalescing | The canister is stopped, time advances 300 seconds, and resume produces exactly one scheduler and one work attempt rather than historical replay. |
| Insufficient cycles | With liquid cycles burned below one provider self-call cost, due delivery is deferred; top-up permits eventual progress without a new logical registration. |
| Terminal cancellation | A normally completed consumer attempt returns `WatchdogDecision::Stop`; the successor is cleared and later cadence points run no work. |
| Scheduler/work-gap cancellation | PocketIC observes `work_dispatched = 1` and `work_started = 0`; cancellation clears both handles and subsequent provider rounds invoke no consumer work. |
| Duplicate demand | Repeated registration endpoints and repeated `ensure_scheduled` calls do not replace callbacks or add another wake-up. |
| Independent timers and trap isolation | Two watchdogs are due together; deliberate primary work trap does not prevent the secondary timer completing, and both reconstruct after upgrade. |
| At most one attempt per generation | Closed registry transitions accept one scheduler and one work token per generation; real snapshots preserve `work_dispatched = 1`, at most one start, and at most one completion per cadence. |
| Commit-window ensure | A normally returned `false` endpoint synchronously ensures the cancelled retained registration before returning; repeating it coalesces without another arm. |
| Full inventory | A 64-entry snapshot is strictly identity-ordered and requires 137,423 measured instructions in the probe query. |

Owner-local native tests additionally inject stale scheduler/work generations,
generation rotation, terminal cancellation with queued tokens, and every
policy/directive transition. Those tests establish exhaustive transition
behavior; the PocketIC cases above establish message commit/rollback behavior.

The same PocketIC flow measured call-context counter type 1. Values are one
local run and are regression subjects, not fixed protocol ceilings.

| watchdog | 23,183 | 5,300 | 25,731 | 9,902 | 19,530 | 19,523 |

The watchdog no-op work wrapper is 386 instructions below the comparable
after-completion work wrapper in this run. Its deliberate extra scheduler
message costs 19,530 measured library instructions.

PocketIC balance deltas across one due dispatch were 15,357,721 cycles for
`Once`, 15,366,757 for after-completion, and 30,731,381 for watchdog. The
watchdog-minus-after-completion delta was 15,364,624 cycles, representing the
extra provider self-call plus its scheduler execution in this environment.
This is an observed end-to-end balance charge, not a fixed mainnet price.

A trap or instruction exhaustion has no end counter and commits no work sample.
The next scheduler reports the prior dispatch as `unacknowledged`; it does not
claim which failure occurred.

### Frozen-subject adjustment

The Patch 1 plan also named isolated stale scheduler/work no-op instruction
probes. Production callback tokens are private and the library exports no
executor route, so a canister cannot construct those calls without adding the
very alternate ingress path the design forbids. Patch 6 therefore keeps stale
generation injection in owner-local native tests and reports no fabricated IC
measurement. The 64-entry inventory measurement is hosted by the separate
recovery probe so benchmark-only capacity setup does not contaminate the four
size cohorts.

Raw physical Rust lines in `crates/ic-timers/src` increase from 2,044 at the
0.2 baseline to 7,380, a delta of 5,336 lines (261.1%). Of the current total,
1,854 lines are the dedicated registry/runtime/snapshot test modules and 2,988

PocketIC sources add 1,326 non-published lines.

The increase is substantial but concentrated in one bounded registry, one
provider binder, policy-specific state, and owner-local evidence. It adds no
second runtime, fallback registry, compatibility shim, persisted timer model,
or downstream dependency.

## Downstream adoption sketch

### IcyDB

Generated IcyDB code can replace `STARTUP_WATCHDOG_TIMER:
Option<ic_cdk_timers::TimerId>` with one volatile
`Option<WatchdogRegistration>`. It can remove `STARTUP_DRIVER_ACTIVE`,
`STARTUP_DRIVER_CADENCE_TIME`, the serial interval arm, and the zero-delay
post-completion `clear_timer` workaround. The existing fixed identity and
one-second cadence register through `reconcile_watchdog`; the synchronous
callback maps Ready or terminal failure to `Stop`, Recovering progress to
`Continue`, and its existing classified completion to `TimerCompletion`.

The adapter result mapping is frozen as follows: a normally completed recovery
unit that remains pending is `TimerCompletion::success(1)` plus
`WatchdogDecision::Continue`; a returned operational failure is
`retryable_failure(completed_units)` plus `Continue`; pre-existing Ready is
`no_work()` plus `Stop`; Ready reached by returned work is
`success(completed_units)` plus `Stop`; and durable terminal database failure
is `invariant_failure(completed_units)` plus `Stop`. Trap or instruction
exhaustion returns no result and commits no completion. This mapping is covered
by the IcyDB-shaped owner-local fixture without importing IcyDB authority.

`__icydb_startup_init` and `__icydb_startup_post_upgrade` remain lifecycle
participants, but initialize/reconcile the shared runtime before application
hooks. The existing commit-guard `STARTUP_RECOVERY_WAKEUP` seam remains useful:
its installed function calls `ensure_scheduled` synchronously before a retained
marker error returns. Durable readiness, startup failure, commit markers,
recovery paging, logging, and error classification remain entirely IcyDB-owned.
IcyDB should rerun its startup timer, schema-application, commit-window, and
Wasm-cost tests before removing its pinned direct watchdog dependency.

### Canic

Canic can replace its private `TimerControl`, `TimerOps` provider wrapper,
copyable `TimerId`, per-entry provider handle/control fields, and duplicate
schedule/execution/outcome counters with policy-specific `ic-timers`
registrations and snapshots. Its `TimerMetrics` and timer-specific `PerfOps`
records can be projected from `TimerCounters` and `TimerPerformance` after
focused adapter tests prove every existing status and metric row. Later Canic
adoption work confirmed that the global `TimerScheduled` increment was
test-only and not publicly projected, so it is removed rather than retained as
parallel instrumentation.

Canic still owns its closed built-in keys, dynamic application IDs, domain
predicates, retry decisions, and lifecycle composition. It should call
`initialize_runtime` before synchronous timer reconstruction, retain only the
registration capabilities needed for cancellation/reconciliation, and adapt
`TimerSnapshot` into its current public DTOs. Suspension/resumption can iterate
those Canic-owned capabilities without retaining a second timer state machine.

Canic's current `TimerApi::set` and `set_interval` return handles directly.
The adapter must instead return a typed result through those methods and their
macros so registry capacity and identity validation cannot panic, evict an
existing timer, or be silently ignored. Closed built-in identities are
prevalidated and registered before application hooks. Dynamic identities use
the monotonic application ID for uniqueness and must encode the operator label
within the 64-byte-per-component contract; Canic's current 96-byte timer-name
projection must be hard-cut or explicitly adapted and tested.

IcyDB, Canic, and applications share a registry only when Cargo resolves one
`ic-timers` package ID. Downstream dependency-unification checks are part of
both adoption gates.

The read-only adoption inventory on 2026-08-13 found these direct provider
owners still to resolve:

- IcyDB generated production startup code and its `icydb` re-export;
- IcyDB's `startup_timer` test canister and `sql_perf` audit canister; and
- Canic's production `ops/runtime/timer.rs` boundary.

Production owners must migrate. Fixture/audit owners may remain direct only as
named exclusions that do not claim shared inventory. The provider's 250
outstanding dispatches are a canister-wide semaphore; `ic-timers`' maximum 128
owned handles is a state bound, not a reservation against that semaphore.
The 0.3.0 publication prerequisite is now satisfied; dependency unification,
direct-provider cleanup, and downstream integration evidence remain open.
