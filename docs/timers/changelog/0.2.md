# 0.2 design slice

Status: release-ready design slice; Canic and IcyDB feedback follows 0.2.0

## Objective

Freeze the provider-neutral identity, snapshot, counter, outcome, measurement,
and epoch contract before implementing registry storage or callback
instrumentation. The contract must be a semantic superset of Canic's existing
timer operator surface.

## Deliverables

- Review and accept the
  [observability and Canic parity contract](../design/observability.md).
- Add bounded `TimerIdentity` and portable policy, state, outcome, counter,
  performance, scope, and snapshot value types.
- Fix deterministic ordering, counter invariants, outcome transitions,
  saturation behavior, and epoch resets in unit tests.
- Define cheap lookup of functional state such as
  `consecutive_expected_failures` by timer identity.
- Add focused Canic adapter fixtures and tests that prove existing status and
  metric projections without depending on Canic DTOs from this crate.

## Candidate implementation

- `snapshot` directory module with bounded structured identity and stable
  ordering.
- Configured policy, effective scheduling mode, checked directive snapshot,
  registration, process condition, pre-armed successor, and timer state types.
- Separate completed and interrupted outcomes, work count, timestamps, and
  functional consecutive expected-failure state.
- Saturating request, arm, start, completion-class, cancellation, stale,
  coalesced, and interruption counters.
- Total, latest, and maximum instruction and elapsed-duration aggregates with
  explicit sample counts.
- Runtime epoch scope with an explicit observation reset.
- Local Canic-shaped projection fixture plus bounds, ordering, transition,
  partition, missing-measurement, saturation, and epoch tests.
- Peer-informed hygiene: stricter lints, rustdoc and workflow-pin gates,
  dependency-update automation, non-exhaustive public errors, a recurring
  audit, and one explicit safety boundary.
- Release automation that finalizes the populated root changelog during the
  version bump and only publishes a clean package whose version tag points to
  `HEAD`.

The downstream Canic and IcyDB review is intentionally before registry or
runtime wiring. A real Canic adapter test remains a migration criterion before
removing Canic's parallel instrumentation.

## Review notes

Version 0.2.0 is intentionally a public, provider-neutral design slice for
downstream review. Releasing it does not claim that registry storage, runtime
instrumentation, recovery behavior, or consumer migration is complete. As a
pre-1.0 contract, it can be revised directly from concrete Canic and IcyDB
feedback before those authority-bearing runtime pieces are added.

## Not in this slice

- Canister-global registry storage or callback ownership.
- Runtime measurement collection or production consumer migration.
- Lifecycle reconstruction.
- Pre-armed watchdog behavior or PocketIC recovery claims.
- Removal of Canic's existing timer instrumentation.

Those implementation steps follow only after the snapshot contract and parity
fixtures are reviewable.

## Exit criteria

- Every required field and counter has one documented meaning.
- Starts and completions remain separate, with interrupted work representable.
- Consecutive expected failures are modeled as functional per-timer state.
- A local Canic-shaped fixture proves that the current timer status,
  scheduling, counter, and instruction fields can be projected without loss.
- The new public value types and transition tests pass the native and Wasm
  checks on the supported toolchains.

Before Canic removes its existing timer instrumentation, a real downstream
adapter test must establish the same projection against Canic's current DTOs.
