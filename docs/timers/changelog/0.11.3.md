# 0.11.3 completion and control simplification

Status: released 0.11.3.

## One ordinary checked-completion failure exit

`TimerRegistry::complete_ordinary` previously finalized directive-resolution
failure and generation-allocation failure in separate branches. Both stopped
control, classified completion as an invariant failure with the consumer's work
count, and applied the same declaration-lifetime/pending-unregister rule through
early removal exits.

Completion now prepares its selected successor and inert directive observation
through the existing checked operations, then handles either control failure in
one branch. The existing `stop_ordinary_completion` owner still selects the
terminal reason, records the stopped directive and completion, and returns the
typed failure. The common method exit applies declaration removal once; two early
removal exits are deleted. No new error type, policy layer or alternate completion
implementation is introduced.

Ordering is unchanged: exact running-work authorization and pending-command
arbitration precede resolution; explicit consumer invariant failure still stops
directly. A winning exact reconciliation discards the callback proposal before
validation. Successful directive resolution precedes the independently checked
snapshot projection, which precedes successor selection and checked allocation.
Projection errors retain their existing registry error without allocating a
generation. Allocation failure retains the running state until terminal
finalization. Successful arms and normal stops retain their observations,
cancellation accounting, provider effects and lifetime rules.

Watchdog completion remains separate: its scheduler has already committed a
successor, and its completion accounting and rollback contract differ. No public
signature, snapshot shape, generation sequence, dependency or storage format
changes. This private behavior-preserving cleanup fits 0.11.3; no binding generator,
downstream adapter or compatibility path needs updating.

## One Watchdog request mode update

`TimerRegistry::ensure_watchdog` previously selected and committed scheduling mode
separately for initial and replacement arms, repeating the successful-allocation
check. Each request now projects its mode and requested delay together. One update
commits that mode only when the existing scheduler owner returns an `ArmWakeup`
effect. Its failed arms return cleanup or no effect, and coalesced or pending
requests return no effect; none changes the active mode.

Request counts and requested-delay observations still record accepted requests
even when they coalesce, pend or fail allocation. Equal-deadline reconciliation
therefore retains the armed mode while recording the new requested delay.
Cadence deadlines remain checked only in the inactive branch: a scheduled cadence
ensure at maximum time coalesces without calculating an unused overflowing
deadline. Input deadline errors still return before request accounting. Dispatched
and running work keep their distinct pending-command rules and existing token
authority; completion remains a separate protocol operation. No extra state,
helper, public API or compatibility path is introduced.

## Direct token ownership in delegated contexts

The private `CallbackContext` type contained only a `CallbackToken`. Its methods
forwarded identity reads and control calls without validation, state changes,
cleanup or lifecycle ownership. `OnceContext`, `AfterCompletionContext` and
`WatchdogContext` now store that token directly. The intermediate type,
constructor and forwarding methods are deleted.

Every mutation still calls the same policy operation with the token's borrowed
claim and `Some(&token)`. `apply_claim_transition` remains the shared authority
boundary: it validates exact running-work ownership before detaching provider
handles or invoking the registry operation. Expired contexts therefore still
return `RegistrationExpired` before mutation; identity remains inert metadata.
Provider restoration, retirement and callback rollback paths are unchanged.
Constructors used by callback erasure retain their existing signatures.

The public context types, method sets, non-clone capabilities and callback
signatures remain unchanged. Their fields remain private; no public constructor,
conversion or token access is added. The policy-specific capability boundary is
worth keeping, while its forwarding-only private layer adds no separate contract.
There are no generated artifacts or downstream adapters to update for this private
change. The architecture and current callback-authority design document now name
the shared transition boundary as the validation owner.

## Verification and delivery scope

The existing `ordinary_terminal_failures_respect_declaration_lifetime` matrix
retains initial, replacement and completion allocation failures for both ordinary
policies and both declaration lifetimes. Two completion subjects now combine real
running work at maximum generation with an oversized retry delay or deadline
overflow. They require `DelayOutOfRange` or `DeadlineOverflow` respectively,
demonstrating validation precedence over generation exhaustion. Retained cases
check terminal reason, one invariant completion rather than success, preserved
reported work count and the stopped directive. Transient cases require declaration
removal and expired claims. The single matrix exceeds the configured line limit;
its local expectation explains that scope rather than introducing fixture machinery.

Focused existing subjects also include:

- `exact_ordinary_reconciliation_discards_invalid_callback_proposals`.
- `explicit_invariant_failure_still_overrides_exact_ordinary_reconciliation`.
- `relative_exact_reconciliation_preserves_request_observations_after_suspension`.
- `ordinary_directive_matrix_preserves_mode_and_checked_deadline`.
- `illegal_once_recurrence_and_invariant_result_stop_truthfully`.
- `nested_cancel_and_ensure_use_latest_request_order`.
- `explicit_unregistration_consumes_scheduled_and_running_claims`.
- Schedule-resolution and public snapshot-conversion negative fixtures, plus the
  runtime ordinary suspension, context expiration and provider-binding subjects.

Existing Watchdog fixtures now also check:

- `watchdog_exact_replacement_rejects_stale_delivery_and_generation_exhaustion`:
  relative replacement commits its mode and requested delay; equal absolute
  reconciliation preserves that mode and records no relative delay; a later
  cadence ensure at maximum time preserves state and mode while recording cadence.
  Its stale-delivery and terminal completion-allocation checks remain.
- `watchdog_requests_preserve_dispatch_authority_until_completion_replaces_the_pair`:
  ensures and exact requests preserve mode as well as dispatched/running authority
  until completion applies the winning command.
- `watchdog_terminal_failures_respect_declaration_lifetime`: a retained immediate
  replacement at maximum generation keeps its cadence mode while recording zero
  requested delay. Both lifetime cleanup cases remain.

The existing immediate initial/replacement, overdue coalescing and pending-command
precedence fixtures remain applicable. These changes introduce no new test suite.

Context forwarding was traced through all three callback constructors and all
public context methods. Existing behavior fixtures remain appropriate without
source-name assertions or new fixtures:

- `once_context_can_restore_scheduling_after_nested_cancel` and
  `after_completion_context_can_restore_recurrence_after_nested_cancel`.
- `retained_once_context_expires_after_its_work_attempt`.
- `watchdog_running_immediate_context_targets_that_attempts_successor` and
  `watchdog_nested_cancel_then_ensure_retains_committed_successor`.
- `retained_watchdog_context_expires_without_clearing_successor` and
  `watchdog_deadline_context_arbitrates_and_expires`.
- The ordinary suspension, registry work-authorization and provider failure
  fixtures retain their separate roles.

Tests, builds, lint gates and deployment validation remain maintainer-owned and
have not been run. Updated native fixtures establish no fresh execution, IC
rollback, provider-heap or performance result. Changed Rust was formatted. Diff
whitespace checks, prepared changelog and release-note preflights, current 0.11.2
release-truth checks and locked offline metadata checks for both workspaces passed.
These checks do not validate runtime behavior. Cargo versions and both lockfiles
remain unchanged; all Git and release execution remains maintainer-owned.
The 0.11.3 section is undated and `Unreleased` is empty. Downstream work remains
deferred.
