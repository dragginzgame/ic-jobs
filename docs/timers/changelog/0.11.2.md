# 0.11.2 callback acceptance and cancellation ownership

Status: released 0.11.2.

## One acceptance and callback selection operation

`TimerRegistry::begin_ordinary` and `begin_watchdog_work` return the corresponding
entry's typed callback only after accepting the exact claim, policy, work role,
generation and eligible scheduled/dispatched state. They advance to running state
and record the work start before returning the callback. Rejected delivery returns
`None`, preserving stale accounting and withholding the callback.

Both runtime work dispatchers receive that callback in the same registry borrow
that consumes its provider handle and accepts work. They release the borrow before
borrowing or invoking the consumer closure. The separate `ordinary_callback` and
`watchdog_callback` methods, their second registry borrow and their impossible
post-acceptance lookup-failure branches are deleted. `CallbackAcceptance` is also
deleted: the returned callback now represents successful acceptance directly.

With those lookup callers gone, `running_work_entry` had only context validation
left. Its read lookup is folded into `validate_running_context`, deleting the
single-caller helper and its discarded entry result. The shared
`Entry::owns_running_work` predicate remains authoritative for contexts and both
mutable completion lookups.

Inspection established that these lookups had no production caller other than
the immediate dispatch step after successful acceptance. Neither suspension,
consumer code nor provider operations occurred between those steps, so the second
lookup re-proved authority established by acceptance. Its standalone negative
assertions served the removed entry points and are removed with them.

Delegated contexts and completions remain independently authorized through
`owns_running_work`: they can arrive later, after suspension or supersession.
Provider installation and effect confirmation also retain their distinct checks.
No callback becomes public control authority, and consumers receive the same
policy-specific context. Ordinary callback-borrow failure still records terminal
invariant failure without invoking or measuring work; Watchdog callback-borrow
failure still traps. Completion, provider effects, measurement scope, cancellation
arbitration and Watchdog rollback rules are unchanged.

This is a private behavior-preserving patch on the 0.11 line. Public signatures,
snapshot shapes, storage formats and dependencies are unchanged. No generated
bindings or downstream adapters need updating; no compatibility path is retained.

## Cancellation state and allocation ownership

Ordinary cancellation selects its effect directly from inactive, scheduled or
running state. It no longer copies the pre-cancellation registration or computes
transient removal separately from Watchdog cancellation. Both policies report
whether their final state is inactive; the registry applies the declaration
lifetime once after selecting the effect. Inactive retained declarations preserve
their reason and all observations; inactive transient declarations are removed.
Running commands, sticky unregister, immediate cancellation accounting and selected
provider cleanup remain unchanged.

`TimerControl::next_generation` previously served ordinary arming and cancellation,
as verified in the 0.10.23 implementation. Since 0.11 cancellation allocates nothing,
it had only `arm_deadline` left. Checked allocation now lives directly in that
operation, before either the counter or scheduled state changes. Overflow still
leaves the previous state and generation untouched until the registry chooses its
terminal handling. The helper is deleted without adding another allocator path.

## Verification and delivery scope

Existing registry and snapshot fixtures now assert that acceptance returns a
callback or no callback rather than a status enum. The running-work boundary
matrix checks duplicate acceptance returns no callback for Once, AfterCompletion
and Watchdog. Its unstarted, wrong-role, stale-claim, stale-generation, completed
and removed-token checks remain at delegated-context and completion boundaries,
including unchanged inventories after those rejections.

The existing fresh-cancellation fixture is extended and renamed to
`fresh_cancellation_preserves_retained_declarations_and_releases_transients`.
It covers both declaration lifetimes for all three policies, requires no effect
or control failure, checks repeated cancellation preserves the complete retained
inventory, and requires transient cancellation to expire the claim. Existing
maximum-generation cancellation, running command-order and sticky-unregistration
fixtures cover the other state exits. The control subjects
`completion_arms_the_supplied_deadline`,
`stopping_invalidates_delivery_without_allocating_and_rearm_uses_next_generation`
and `exhausted_generation_rejects_successors_without_preventing_stop` retain
allocation, stop/rearm and failed-allocation atomicity coverage.

Focused runtime subjects include:

- `once_owns_one_provider_handle_and_executes_without_registry_borrow`.
- `ordinary_callback_borrow_failure_stops_without_invoking_or_measuring_work`.
- `after_completion_rearms_from_actual_completion_time`.
- `suspended_once_work_allows_other_timers_and_arbitrates_external_commands`.
- `stale_reused_identity_callback_cannot_change_handles_or_measurements`.
- `watchdog_scheduler_prearms_successor_before_synchronous_work`.
- `watchdog_cancellation_clears_successor_and_queued_work`.
- `retained_watchdog_context_expires_without_clearing_successor`.
- The existing Watchdog completion/provider fault fixtures and ordinary
  context-expiration fixtures.

Tests, builds, lint gates and deployment validation remain maintainer-owned and
have not been run. These fixture updates claim no fresh execution result, IC
rollback evidence, provider heap bound or measured performance improvement.

Changed Rust was formatted. Diff whitespace checks, prepared changelog and
release-note preflights, and current 0.11.1 release-truth checks passed. Locked
offline metadata checks resolved one `ic-timers` package at the unchanged workspace
version in each of the root and testing workspaces. These are formatting and
metadata checks, not runtime validation.

Cargo versions and both lockfiles remain unchanged. The 0.11.2 heading is undated,
`Unreleased` is empty, and all staging, commits, bumps, tags, pushes and publication
remain maintainer-owned. Downstream work remains deferred.
