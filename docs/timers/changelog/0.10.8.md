# 0.10.8 ordinary state ownership and compact handoff

Status: released 0.10.8.

## One ordinary state model

Ordinary entries previously stored pure registration state, an independent
inactive reason and an independent pending command. Active states carried an
unused reason, and every terminal path had to stop control, clear its pending
command and assign its reason separately.

Private `TimerRegistration` now has three states: inactive owns its reason,
scheduled owns its generation and deadline, and running owns its generation
and optional command. The two independent entry fields are deleted. The command
type lives with that state model; the registry still owns arbitration and exact
running-work authorization. It can change the command only through running
state. State access remains private to the crate, without a public authority
path or snapshot mutation interface.

Fresh control constructs `NeverScheduled`. Checked immediate cancellation
constructs `Cancelled`, while cancelling inactive control preserves its reason
and cancelling running control leaves the attempt available for registry
arbitration. Completion selects `Stopped` or `Cancelled`; explicit invariant
failure selects `InvariantFailure`; checked or provider failure selects the
corresponding `ControlFailure`. Each stop replaces the complete state and
therefore discards any running command. Paired reason writes and explicit
pending-command clearing are deleted.

## One arming and stopping operation

Eligible ordinary requests and authorized completion successors use the same
checked `arm_deadline` operation. It allocates before replacing state, so failure
preserves the current generation and running command until registry terminal
finalization. A successful arm drops the completed attempt's command by replacing
running state with scheduled state. The separate optional-successor
`complete_running` operation is deleted; completion without a successor stops
directly with its selected reason and allocates nothing.

Scheduling eligibility, stale-token rejection, pending ensure/exact/cancel
ordering, sticky unregister and invariant-failure priority are unchanged.
Registry effects retain the same tokens, delays, cleanup selection, counters
and declaration-lifetime behavior. The snapshot projection reads the new private
state but emits the existing public shape. Watchdog behavior, effect confirmation,
handle restoration and callback rollback rules are unchanged.

This is a private volatile representation change suitable for a patch release.
No public API, persisted format, generated artifact, downstream adapter or
compatibility path changes are required.

## A handoff that survives release execution

The compact status previously repeated a claimed current commit/tag and described
the upcoming release as prepared. Release finalization updated its workspace
version projection and the release-note status, leaving that prose stale.

The handoff now describes architecture, ownership, evidence boundaries and
unresolved scope. It retains the single workspace-version projection required by
release tooling. Cargo, dated changelog sections and release-note statuses remain
authoritative for version and preparation/release state; delivery references live
in the relevant release notes. No new marker, prose parser or release gate is
introduced, and release execution remains maintainer-owned.

## Focused verification

The maintainer's Clippy run reported redundant `pub(crate)` qualifiers on types
inside the private control module. The declarations now use `pub`, including the
pending-command type exposed by the internal state enum. The module remains
private and the crate facade exports none of these types. Consumer visibility
and runtime behavior are unchanged; the automated contributor has not rerun Clippy.

Existing control fixtures now check reason-bearing inactive state and the shared
arming/stopping operations. The running-request fixture checks that pure control
preserves an existing unregister command while leaving arbitration to the registry.
The exhausted-generation fixture also checks that
failed arming preserves a running pending command and that stopping still needs
no generation allocation. Existing registry and runtime fixtures retain fresh
declaration, pending-order, inactive-reason, stale-token, terminal-lifetime,
provider-cleanup and restoration coverage. No broad new test suite or source-text
assertion is added.

Tests, builds, lint gates and deployment validation remain maintainer-owned;
none were run during preparation. No new runtime, recovery or performance result
is claimed. Downstream work remains deferred.

Changed Rust is formatted. Diff whitespace, current release-truth and read-only
0.10.7-to-0.10.8 note/handoff checks passed. The public crate facade, Cargo
manifests, both lockfiles and Git index are unchanged. No version bump or Git
release operation was run during preparation.
