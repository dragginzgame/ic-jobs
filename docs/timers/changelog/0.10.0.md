# 0.10.0 Watchdog failure classification and control ownership

Status: released 0.10.0.

## Watchdog stop classification

Invariant failure takes precedence over pending cancellation when Watchdog work
completes. The retained declaration reports `InactiveReason::InvariantFailure`
and `TimerProcessCondition::Failed`; cancellation is counted only when it wins
arbitration. Completion outcome accounting, successor cleanup, sticky unregister
and transient removal retain their existing owners. This changes observable
snapshot/counter semantics and therefore belongs on the 0.10 minor line.

## Private control ownership

Ordinary scheduling returns only an optional initial/replacement arm kind. The
registry obtains generation and deadline from the resulting control registration.
The superseded scheduling-action enum and duplicated state fields are deleted.
Earliest/exact selection, coalescing, pending commands and checked generation
allocation remain required.

Owned provider roles are derived from immutable entry policy and handle slot.
The copied role field is deleted; consumption still rejects mismatched policy,
role, claim and generation. Temporarily detached handles retain their complete
callback token so restoration and cleanup can proceed after entry transitions.

## Scope and verification

The implementation is confined to this repository. Downstream work remains
deferred at the maintainer's request. There are no compatibility aliases,
migrations, dual implementations or generated binding changes.

Existing native control fixtures now observe state instead of the removed action.
The registry arbitration matrix includes invariant failure combined with cancel
and unregister, checking classification, counters and successor cleanup. A focused
runtime fixture covers cancellation plus invariant failure for both declaration
lifetimes and actual successor-handle cleanup. A provider-role fixture rejects
same-claim mismatches and checks complete tokens through detach/restore.

These fixtures and maintained provider replacement/restoration tests are the
focused verification subjects. Formatting, diff whitespace, current release-truth
and target-note structural preflight checks passed during preparation. Tests,
builds, lint gates and release execution are user-owned. No new runtime or recovery
result is claimed until those subjects have been executed. Cargo versions, both
lockfiles and Git release state remain unchanged during preparation.
