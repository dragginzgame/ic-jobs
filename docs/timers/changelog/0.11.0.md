# 0.11.0 cancellation and Watchdog generation ownership

Status: released 0.11.0.

## Contract and hard-cut boundary

Cancellation stops or queues a stop request for existing work without allocating
callback generations. Ordinary and Watchdog cancellation no longer advance their
allocation counters. The ordinary control cancellation allocator and both
cancellation exhaustion branches are removed. No earlier cancellation
implementation or compatibility mode remains.
Ordinary request failure finalization now lives directly in its only remaining
caller; the cancellation branch and its shared terminal helper are deleted.

For scheduled or dispatched work, inactive state rejects old deliveries and the
runtime clears the selected provider handles. Later scheduling and dispatch still
allocate fresh, non-wrapping generations. Running work retains pending-command
arbitration; cancellation does not interrupt an invocation already executing.
Retained and remove-on-stop lifetime rules, exact registration claims, callback
roles and independent handle-generation checks remain authoritative.

This changes observable semantics and therefore requires 0.11.0. Cancellation at
maximum generation now reports normal cancellation rather than
`ControlFailure(GenerationExhausted)`, with `Cancelled` state and cancellation
accounting. Generation values observed after cancel/rearm no longer include
cancellation increments. Scheduling beyond the generation limit still fails;
expired claims, unavailable runtime access and provider failures retain typed
errors. Cancellation's public Rust signatures remain unchanged; the Watchdog
snapshot hard cut below changes its observation shape.
Reconciliation to `None` and non-running unregistration use the same cancellation
owner and likewise no longer fail merely because a counter is exhausted. Cancelling
an already inactive retained declaration remains an idempotent no-op that preserves
its existing inactive reason.

## One Watchdog allocation history

Watchdog control now owns one generation counter. A scheduler dispatch advances
it once and stamps both the cadence successor and queued work with that generation.
Their callback roles and separate provider slots distinguish the deliveries. The
independent attempt counter, paired-increment helper and attempt-only exhaustion
path are deleted; no alternate allocation model remains.

The prior reason for separate clocks was scheduler replacement independent of
work attempts. Inspection of every `arm_scheduler` caller established a stronger
invariant: a request cannot replace a successor while work is dispatched or running.
Cadence/immediate ensures coalesce or become pending commands, and exact scheduling
becomes a pending command. Normal completion expires the work attempt before a
replacement becomes authoritative. A recovery scheduler retires an unacknowledged
dispatched attempt before allocating the next pair. The generation never needs to
identify two different live dispatches for the same claim.

The old attempt-only exhaustion fixture seeded a history production could not
construct. The scheduler's initial arm allocated first; replacement advanced
only that clock, while dispatch and the superseded cancellation advanced both.
The scheduler therefore exhausted before an independent attempt overflow was
reachable. Its real allocation boundary remains covered by the shared-counter
fixtures rather than preserving a test-only counter combination.

Generation exhaustion remains selected before deadline overflow, and the deadline
is validated before advancing the counter. State, exact claim and role remain
required at work acceptance, delegated control, provider binding and confirmation.
Dispatch effects also require equal generation stamps in addition to correct roles
and one exact claim before any provider call. Confirmation validates the effect and
current state before deduplicating successful accounting. Provider cleanup,
Watchdog work-message rollback and the pre-armed recovery protocol remain separate.

Public timer-control signatures remain unchanged. With no replacements, the
initial arm is generation 1, its first successor and work share generation 2,
and the next dispatch shares generation 3. Replacement and cancel/rearm can
introduce gaps; generation values are delivery stamps, not work counts. Use the maintained event
counters for work accounting. This is another observable semantic hard cut within
the prepared 0.11.0 boundary. All library authority is volatile; no stored-format
reader, migration, alias or dual-runtime mode is introduced.

## Direct attempt status in snapshots

The shared dispatch generation removes the independent generation from the work
attempt observation. `WatchdogAttemptSnapshot` and its root export are deleted,
including its `generation()` and `status()` accessors. The authoritative
`WatchdogRuntimeStateSnapshot::AwaitingWork` shape is now:

```rust,ignore
AwaitingWork {
    successor_generation: u64,
    successor_deadline_ns: u64,
    attempt_status: WatchdogAttemptStatus,
}
```

Consumers replace `attempt.status()` with `attempt_status`, and use the parent
`successor_generation` (or `TimerSnapshot::generation()`) for the shared delivery
stamp. Scheduled/running registration projections and process conditions retain
their meanings. Snapshots remain inert, never callback or provider authority.
There is no compatibility export or alternate reader for the removed shape.
No repository-owned generated binding or persisted codec uses it. Downstream
adapter edits are deferred; consumers exposing their own wire or stored snapshot
format must inspect that exact format before changing their representation.

## Verification and delivery scope

The maintained fixture updates are:

- Ordinary maximum-generation cancellation covers both ordinary policies and
  both declaration lifetimes. It checks normal cleanup, stale delivery,
  cancellation accounting, unchanged allocation history, idempotent retained
  cancellation, expired transient claims and rejection of a new arm at the limit.
- Watchdog maximum-generation cancellation covers scheduled and dispatched
  work with the shared allocation history exhausted, for both lifetimes.
  It checks the selected handle set, unchanged counters, inactive cancellation,
  stale scheduler/work delivery and rejection of a new arm at the limit.
- The existing ordinary control stop/rearm and Watchdog queued-delivery fixtures
  now assert fresh generations without cancellation increments and reject old
  tokens after rearming. No cancellation-exhaustion assertions remain in the
  terminal-failure matrices; real allocation failures remain covered there.
- The existing native provider cleanup fixtures now rearm retained ordinary and
  Watchdog declarations after cancellation, check the new generation sequence
  and execute only the resumed work with the expected live handle count.
- The dispatch-authority fixture covers cadence, immediate and exact requests
  during both dispatched and running work, including initial scheduler replacement.
  It checks unchanged paired snapshots, wrong-role rejection, retained context
  authority and expiration of old work and scheduler tokens after completion.
- The protocol snapshot fixture reads `attempt_status` directly and checks both
  dispatched-to-scheduled and running-to-running registration projections.
- Provider-role fixtures retain stale-generation and policy-role rejection,
  detachment/restoration and separate slot ownership. Changing a shared-generation
  token to the other Watchdog role constructs the valid paired token; installation
  must reject its occupied slot rather than classify that token as stale. Direct
  dispatch through the wrong role still rejects. Confirmation fixtures retain
  cross-claim and mixed-generation rejection before duplicate accounting.
- The runtime mixed-generation fixture builds two consecutive dispatches from
  one real claim, crosses the old/new successor and work tokens in both directions,
  and requires `OwnershipInvariant` before provider arms with unchanged inventory.
  The existing cross-claim runtime fixture remains separate.
- Exhaustion matrices retain initial, replacement, dispatch and completion
  allocation failures, deadline failure, terminal cleanup, lifetime removal and
  generation-first error precedence. The removed attempt-only exhaustion case
  is replaced by dispatch exhaustion at a real maximum-generation scheduler;
  retained-successor and unacknowledged recovery fixtures remain maintained.

Tests, builds, lint gates and deployment validation remain maintainer-owned;
none were run for this change. Native fixtures do not simulate IC rollback or
the provider's retained deadline queue. Required real-platform subjects include
`cancellation_between_scheduler_and_work_makes_late_provider_delivery_harmless`,
`commit_window_ensure_stop_resume_and_large_overdue_time_remain_bounded`, and
`provider_replacement_churn_preserves_cancellation_and_reports_memory`, alongside
the complete release gate. Fixture changes await execution; they establish no
fresh successful result or expanded recovery claim.
